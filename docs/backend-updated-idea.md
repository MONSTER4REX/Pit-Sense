# PitSense — Updated Backend Simulation Plan

## 1. Product objective

PitSense should become a **historical replay + controlled counterfactual simulation** system.

The system must not compare a PitSense-controlled P2 car against a frozen historical P1 car after a Shock Event. That would create an unfair comparison because only one car would be allowed to adapt.

Instead:

- Before the fork, both cars follow the real historical race data.
- When a Shock Event is injected, **both cars react to the same changed race environment**.
- The P2 car is controlled by **PitSense**.
- The P1 car is controlled by a **Baseline Strategy** representing a conventional, non-PitSense decision process.
- After the fork, both cars continue to adapt as the simulated race state changes.
- The final comparison is explicitly labelled as a **counterfactual projection**, not a claim about what actually happened.

## 2. Core simulation model

### Phase A — Historical replay

The simulation starts at Lap 1, using the selected race's real FastF1 data.

For each tick/lap, the backend provides the current historical state for:

- our car: actual P2 finisher
- opponent: actual P1 finisher
- lap number
- tyre compound
- tyre age
- position
- gap
- pit status
- relevant historical race events

Until a Shock Event or explicit simulation decision occurs, this is a straight historical replay.

### Phase B — Shock Event

A Shock Event changes the simulated environment at a selected point, for example:

- Safety Car
- VSC
- Rain/weather change

At the Shock Event, both P1 and P2 must reconsider their strategy.

The historical race is now the **baseline reference**, but it is no longer the sole source of future behaviour.

### Phase C — Dual-strategy decision

At every strategic decision point after the fork:

**P2 / PitSense** evaluates:

- tyre degradation
- pit-lane loss
- traffic/rejoin risk
- rival response / cover probability
- strategy graph / total race-time cost
- confidence
- available actions: Pit Now / Stay Out / Extend

**P1 / Baseline Strategy** evaluates the same race state using a deliberately simpler conventional model, without PitSense-specific intelligence.

The Baseline Strategy must be documented as a modelled comparator. Do not call it the "official F1 strategist" because the real teams' proprietary post-shock reasoning is not observable from historical data, and an artificial Shock Event did not occur in the original race.

## 3. Baseline Strategy definition

The Baseline Strategy is an adaptive comparator, not frozen historical behaviour.

It should be deterministic and explainable enough for a fair comparison.

Suggested inputs:

- current tyre age and compound
- basic tyre degradation estimate
- current position
- pit-lane loss
- current gap
- Safety Car/VSC/rain state
- simple pit-window / conventional strategy rules

It must **not** use PitSense's full strategy graph, rival-response scoring, or PitSense-specific explainability stack.

The objective is not to make the baseline weak. The objective is to create a reasonable non-PitSense control condition.

## 4. Decision interface

At a decision point, both strategists should produce a comparable decision object.

Example structure conceptually:

```text
StrategyDecision
  car
  lap
  action: PIT | STAY_OUT | EXTEND
  target_lap
  confidence (PitSense only if supported)
  projected_time_cost
  projected_position
  explanation
  model_type: PITSENSE | BASELINE
```

The frontend can therefore show:

```text
P2 / PitSense      → PIT NOW
P1 / Baseline      → STAY OUT
```

without conflating the two decision systems.

## 5. User-controlled fork

The strategist must be able to accept or override the PitSense recommendation.

Example:

```text
PitSense recommends: PIT LAP 25

[ ACCEPT ] [ STAY OUT ] [ EXTEND ]
```

When the user accepts an action, the simulation creates a **counterfactual fork** at that point.

The fork should record:

- race
- lap
- pre-fork historical state
- Shock Event
- PitSense recommendation
- user-selected action
- P1 baseline decision
- assumptions used for projection

## 6. Counterfactual simulation after the fork

After the fork, the backend must produce a projected lap-by-lap timeline rather than only a single final number.

For each projected lap, calculate the evolving state of both cars using the available modelled assumptions:

- projected tyre state
- projected lap time
- pit-state transition
- position
- gap to opponent
- track-order changes
- relevant strategic decisions

The simulation continues until the projected finish.

Important: the backend must distinguish between:

**Historical state** — observed from FastF1.

**Projected state** — generated by the counterfactual model.

Never mix these silently.

## 7. Opponent adaptation

The P1 baseline car must also adapt after the fork.

It should not simply continue its historical pit schedule.

At each material strategic state change it should reconsider its available actions using the Baseline Strategy.

For example:

```text
Lap 25 — Safety Car

P2 / PitSense: PIT
P1 / Baseline: STAY OUT

Lap 28 — new gap/tyre state

P2 / PitSense: STAY OUT
P1 / Baseline: PIT
```

This produces a real competition between two strategy policies.

## 8. Historical reference track

The original historical race must remain available as a third reference trajectory.

The backend should therefore be able to expose three conceptual timelines after the fork:

1. **Historical** — what actually happened.
2. **PitSense Counterfactual** — what the P2 car's path projects under the selected PitSense decision policy.
3. **Baseline Counterfactual** — what the P1 comparator projects under its own adaptive policy.

This is much more defensible than comparing PitSense against a frozen historical opponent.

## 9. Required endpoints / services

### Race selection

`GET /api/races/available`

Returns races with verified usable FastF1 data.

At minimum, support the validated race set already identified in the project:

- 2024 Canada
- 2023 Netherlands
- 2024 Australia
- 2024 British GP
- 2024 Azerbaijan

### Race session

`GET /api/race/{year}/{event}/session`

Returns the real historical dataset needed to initialize the replay and identify:

- P1
- P2
- lap-by-lap state
- tyre stints
- pit events
- historical Safety Car/VSC/weather events when actually recorded
- result metadata

### Replay WebSocket

`/ws/replay`

Each tick should carry enough state for the frontend to render the current simulation.

Preferred architecture: compute backend-owned strategy state and include it in the tick payload rather than making the frontend independently invoke strategy logic every tick.

Each tick should distinguish whether it belongs to:

- HISTORICAL
- COUNTERFACTUAL

and identify the active scenario/fork.

### Shock Event

Provide an explicit endpoint such as:

`POST /api/simulation/shock`

with an event type and the current simulation state.

The response should confirm:

- event accepted
- fork/state updated
- both strategy policies recomputed
- new recommendations
- confidence/risk for PitSense

### Decision acceptance

Provide an explicit action endpoint such as:

`POST /api/simulation/decision`

which records the user's selected PitSense action and creates the counterfactual fork.

### Counterfactual summary

Provide an endpoint such as:

`GET /api/simulation/counterfactual`

returning:

- historical finish
- PitSense projected finish
- baseline projected finish
- projected finishing gap
- projected gain/loss versus historical
- overtake lap if applicable
- assumptions / limitations
- historical vs projected timeline markers

## 10. Pit-stop modeling

The backend must expose pit-lane state per tick.

If FastF1 does not provide exact sub-lap pit-lane timing, do not invent it.

Use an explicit approximation and label it as such.

For example:

```text
PIT IN
PIT STOP
PIT OUT
```

can be represented across the recorded in-lap/out-lap window if that is all the source data supports.

The resulting post-pit gap/position must come from real data in historical mode and from the model in counterfactual mode.

## 11. Historical-vs-projected data contract

Every time-dependent object should include a mode/status field conceptually equivalent to:

```text
mode = HISTORICAL | PROJECTED
```

This should flow through backend services and WebSocket messages.

The frontend must never have to guess whether a value is real historical data or modelled projection.

## 12. Tick-driven recomputation

This remains the highest-priority technical fix.

The existing problem is that replay ticks advance while strategy panels remain frozen.

Every tick or explicitly chosen throttled interval must update:

- recommendation
- confidence
- risk tier
- explainability
- current What-If state

The chosen update interval must be documented and justified against the 1-second re-optimization requirement.

Proof requirement: replay a race and demonstrate multiple genuinely different recommendation states across different laps.

## 13. Explainability / intelligence weights

The intelligence-weights concept can be adopted as a reusable pattern, but do not claim arbitrary numerical weights are calibrated unless they are actually validated.

A defensible first version is a two-model comparison for tyre-cliff analysis:

```text
Statistical detector weight: X
Regression-model weight: Y
X + Y = 1
```

Show both model contributions transparently.

Do not build a four-source ML/simulation/history/memory blend unless the necessary infrastructure and validation exist.

## 14. Human-readable reasoning

Every PitSense recommendation should include a concise human-readable explanation in addition to factor bars.

Example pattern:

> Stay-out loss: 3.45s vs Pit loss: 22.00s. Undercut gain: 4.12s.

The actual values must be generated from the current state, not hardcoded.

## 15. Race-event endpoints

It is useful to keep event analysis granular and demoable.

Possible explicit services:

- `/api/safety-car-analysis`
- `/api/rain-strategy`

These should be thin orchestration/analysis boundaries over the same core strategy state, not separate duplicate strategy engines.

## 16. Validation requirements

For every supported race:

1. verify the selected race data differs from other races
2. verify P1/P2 identity against the historical result
3. verify tick state changes over replay
4. verify a Shock Event changes both P1 baseline and P2 PitSense decisions
5. verify accepting a PitSense decision creates a fork
6. verify projected data is visibly different from historical data
7. verify the final projected result is labelled as counterfactual

A particularly important test is:

```text
Same historical state
+ same Shock Event
+ two strategy policies
→ different but explainable actions/outcomes
```

## 17. Integrity rules

Never:

- keep P1 frozen while P2 adapts
- call the baseline model "official F1 strategy"
- present projected values as real historical facts
- fabricate sub-lap pit timing
- fabricate energy/fuel data
- invent model weights without evidence
- claim PitSense "changed history"

The correct language is:

> PitSense generated a counterfactual projection under explicit assumptions.

## 18. Implementation order

1. Real FastF1 data wiring
2. Tick-driven recomputation
3. Race selection
4. P2/P1 identity and historical state loading
5. Baseline Strategy engine
6. Shock Event affecting both policies
7. User decision acceptance / simulation fork
8. Lap-by-lap counterfactual projection
9. Pit-lane event state
10. Counterfactual summary and comparison
11. Explainability / two-model comparison enhancements
12. Optional event-specific endpoints
13. Optional energy feasibility investigation

## 19. Definition of done

The simulation is not considered complete until a judge can:

1. choose a real historical race
2. start from Lap 1
3. watch historical data advance continuously
4. inject a Shock Event
5. see both P1 baseline and P2 PitSense reconsider the situation
6. choose Pit / Stay Out / Extend for P2
7. watch the simulation fork
8. see P1 continue adapting under the baseline policy
9. see P2 continue adapting under PitSense
10. compare the resulting projected race outcome with what actually happened
11. clearly distinguish historical facts from projections
